# PsDoctor.Observer.Client

Типизированный доступ к API [наблюдателя](../PsDoctor.Observer/README.md): команды, поток фактов, разбор Server-Sent Events. Windows не нужен — библиотека работает там же, где `HttpClient`.

Кроме потока клиент умеет скачать исходный журнал JSONL, список зарегистрированных результатов рендера, один MP4 по его идентификатору и сырой ETW по явному запросу. Он не принимает произвольные пути к файлам стенда.

## Граница

Клиент не решает ничего: не повторяет запросы, не толкует факты, не знает про ProShow. Отказ наблюдателя приходит наружу устойчивым именем (`program-running`, `bad-scenario`), а не фразой — слова живут у того, кто разговаривает с человеком.

Маршруты и имена отказов клиент не переписывает у себя: они лежат в `Core/Observation/ObserverApi.cs` и общие с сервером.

## Зачем отдельный проект

Клиентов у API может быть сколько угодно: сегодня живых двое — `psdoctor observe` и пульт [`PsDoctor.Workbench`](../PsDoctor.Workbench/README.md), а окно оператора когда-нибудь станет третьим. Библиотека существует, чтобы вторая и третья реализации не появились копированием первой; на пульте это уже проверено — своего HTTP у него нет.

## Что важно знать при правке

**Переподключение — свойство протокола, а не удобство.** Журнал сеанса лежит на диске, поток — окно в него, и клиент, отвалившийся посреди часового рендера, обязан продолжить с номера последнего факта. Сервер к этому готов, `Last-Event-ID` работает, тест это закрепляет.

## Тесты

Идут вместе с серверными — `tests/PsDoctor.Observer.Tests`, на тестовом хосте: клиент проверяется против настоящих маршрутов, а не против заглушки.
