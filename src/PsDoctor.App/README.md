# PsDoctor.App

Пользовательский Doctor на Avalonia. Компактное окно и трей дают обычное открытие `.psh`, холодную проверку проекта, рекомендации и мастер «Решить проблему». Мастер выбирает между быстрым восстановлением служебных файлов, проверкой материала и наблюдением за ProShow; технические названия файлов оператору не показываются. Закрытие окна прячет его в трей; «Выход» завершает Doctor. Выбранный для проверки файл не считается автоматически открытым в ProShow.

Это самостоятельное приложение монтажёра без технической подготовки; удобство и понятность во главе угла. Роль решена [вторым раундом](../../design/tier2/roles.md): **App применяет готовые рецепты** — узнал известную проблему, дал совет с понятным действием, не узнал — молчит. Рецепты создаются в `PsDoctor.Workbench` опытами инженера и агента; Workbench не подменяет это окно и не предназначен для обычной работы монтажёра.

## Что здесь будет

Рабочее поведение задано [спецификацией интерфейса](../../design/field-ui/README.md). Для диагностического запуска App использует Observer.Client только с шагом `launch` и завершает наблюдение через `Stop`, не закрывая ProShow. Адрес берётся из настроек машины, ключ — из профиля, куда его кладёт сторож ([установщик](../../install/README.md)); переменные `PSDOCTOR_OBSERVER_URL` и `PSDOCTOR_OBSERVER_KEY_FILE`, если заданы, главнее — для инженера и стенда. Без того и другого действие недоступно, и мастер просит позвать администратора. Сеансы мастера помечаются `origin: wizard` и хранятся дольше. Для странного поведения и ручного рендера App пассивно подключается к уже работающему ProShow и показывает, когда запись ETW неполная. Кнопка «Закончить наблюдение» видна, пока идёт сеанс; она и «Выход» из трея останавливают сеанс, не закрывая ProShow. Если ProShow не запущен, мастер объясняет, что прошлый сбой не записан, и предлагает запустить проект под наблюдением. Отсутствие рекомендаций не объявляется гарантией здоровья проекта.

Внутренний быстрый рецепт работает с узким списком служебных файлов: `proshow.phd` в каталоге программы и его зеркале `VirtualStore`, а после выбора `.psh` — одноимённый `.pxc` рядом с ним. Каждый существующий файл переименовывается рядом с исходным и может быть возвращён вручную. `proshow.cfg`, `autosave.psh`, временные файлы, медиа и сам `.psh` не трогаются. При работающем ProShow ничего не переименовывается; мастер просит сохранить работу и закрыть программу вручную. Номер, время и результат попыток пишутся в `%LOCALAPPDATA%\PsDoctor\repair-history.jsonl`.

Решено, но в коде нет ([сценарии М1–М6](../../design/tier2/roles.md)): перетаскивание `.psh` на окно; совет по эпизоду детектора — фразу и кнопку к факту, который пишет наблюдатель; кнопка рекомендации о материале, зовущая внешний перекодировщик с готовыми параметрами; дежурство за каждым запуском ProShow — после замера цены; откат к резервным срезам `.bNN` в копию.

## Граница

**Слова живут здесь и только здесь.** В отчёте CLI и в фактах наблюдателя человеческих фраз нет вовсе.

**Окно не повышается в правах.** Это не осторожность: у процесса с повышенными правами перестаёт работать перетаскивание файлов из проводника, и доктор не смог бы принять брошенный мышкой файл шоу.

Avalonia, а не WPF: WPF навсегда закрыл бы общий код с соседним проектом владельца.

## Проверка

`dotnet test tests/PsDoctor.Infrastructure.Tests --filter FullyQualifiedName~ProShowCacheCleanerTests` проверяет точный набор файлов, сохранение байтов и отказ при работающей программе; `RepairHistoryTests` — историю попыток мастера и переходы после ответа оператора. Сборка App и короткий запуск на Windows проверяют загрузку окна и значка трея. На машине Оли перед первым действием проверить путь установленного ProShow и наличие файлов в его реальном профиле.
