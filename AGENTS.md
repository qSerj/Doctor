# AGENTS.md

Этот файл задаёт правила работы Codex с кодом этого репозитория.

## Язык

Проект русскоязычный: документы, комментарии, имена тестов, сообщения коммитов и вывод программы пишутся по-русски. Имена типов, методов и файлов кода — английские, по идиоме C#. Абзац в markdown это одна строка: перенос ставится там, где кончился абзац, а не по ширине текста.

## Разделение работы — с 21.09.2026

**Агент — архитектор и разработчик; владелец — исполнитель прогонов.** Агент проектирует, пишет код и тесты, поддерживает документацию, делает ревью и анализирует полученные журналы. Владелец выполняет сборку, тесты, опыты, deploy, управляет ВМ, ProShow и нашим ПО на стенде, нажимает кнопки и при необходимости снимает экран. Наличие SSH, MCP или другого инструмента не меняет это разделение.

Агент самостоятельно читает и редактирует файлы задачи, использует локальные Git status/diff/log и разбирает готовые результаты. Локальный подсчёт по готовому журналу допустим. Самостоятельно запускать build/tests, валидаторы и проверяемые скрипты, продукт, стендовые команды, опрос состояния или съёмку экрана нельзя. Эти ограничения действуют и для подагентов. Разовое исключение — прямое поручение владельца выполнить конкретную операцию; «делай», «исправь», «продолжай» не передают обязанности оператора.

**Цикл:** реализация и ревью → задание проверки владельцу → завершение ответа → результаты → анализ и следующая правка. Передача идёт файлами через существующий `exchange`: [договор обмена](lab/README.md). Не ждать появления файлов, не опрашивать стенд и не запускать повторы. В ответе назвать пакет/команду и критерий, а после получения результатов — проверенную версию и источник чисел. Статусы: «реализовано», «передано на проверку», «проверено владельцем», «нужна правка». Реализация без результатов не означает проверку или завершение критерия.

**Git.** Fetch/pull/push выполняет владелец — в том числе для Memorex. Локальный коммит открытого проекта делается по явному запросу через проектный [commit-changes](.agents/skills/commit-changes/SKILL.md); после «комить» повторное подтверждение не требуется. Завершение реализации само по себе не разрешает коммит. Не смешивать чужие изменения и не запускать проверки через Git hooks без поручения владельца. Правила и скиллы Memorex не редактировать; порядок локальной записи памяти остаётся её собственным, а синхронизацию выполняет владелец.

**Делегирование.** Для ограниченных простых задач использовать подагентов с явно выбранной `gpt-5.6-luna`, для локальных изменений кода по готовому контракту — `gpt-5.6-terra`. Архитектуру, неоднозначные решения и итоговое ревью оставляет основной агент. Передавать короткое задание, нужные файлы, критерий и ограничения, без всей истории по умолчанию. Не создавать подагента ради одного чтения и не повторять его работу. Если подходящей модели или делегирования нет, сообщить об ограничении; не заменять молча дорогой моделью или отдельной пользовательской задачей.

**Проектные скиллы.** Канонические инструкции — в `.agents/skills/`. Для коммита использовать именно проектную версию, даже если есть одноимённая личная. Передача проверки и анализ результатов — [check-handoff](.agents/skills/check-handoff/SKILL.md); настройка переноса и разбор его отчёта — [lab-transfer](.agents/skills/lab-transfer/SKILL.md). Обычный перенос должен выполняться владельцем самостоятельным скриптом без ИИ.

## Команды для владельца

```bash
dotnet test PsDoctor.slnx                                              # все тесты
dotnet test PsDoctor.slnx --filter "FullyQualifiedName~Кодировка_1251" # один тест по имени
dotnet run --project src/PsDoctor.Cli -- "путь/к/проекту.psh"          # машинный отчёт в stdout
dotnet run --project src/PsDoctor.Cli -- "проект.psh" --pretty         # то же, с отступами
dotnet run --project src/PsDoctor.Cli -- "проект.psh" --anonymize      # обезличенный срез
dotnet run --project src/PsDoctor.App                                  # Avalonia, только Windows
dotnet run --project src/PsDoctor.Workbench                            # пульт наблюдателя, Avalonia, где угодно
lab/observer.sh                                                       # собрать наблюдатель, доставить на стенд, прогнать тесты
dotnet run --project src/PsDoctor.Cli -- observe health                # версия и коммит наблюдателя на стенде
dotnet run --project src/PsDoctor.Cli -- observe run сценарий.txt --follow  # прогон сценария, факты в stdout
```

`observe` требует адреса и ключа: `PSDOCTOR_OBSERVER_URL`, `PSDOCTOR_OBSERVER_KEY_FILE` или ключи `--url`, `--key-file`. У этой подкоманды **своя** таблица кодов возврата: 0 — выполнено, 1 — сценарий не выполнен, 2 — отказ наблюдателя, 3 — сбой окружения.

Отчёт CLI **машинный**: JSON Lines, строка на файл, человеческих фраз в нём нет — слова живут в окне. Отчёт идёт только в stdout, диагностика только в stderr. Коды возврата: 0 — разобран, находок нет; 1 — есть находки; 2 — не файл шоу; 3 — сбой окружения. Лечить и писать в чужой каталог CLI не умеет вовсе.

`TreatWarningsAsErrors` включён на весь solution — любое предупреждение ломает сборку. Версии пакетов живут только в `Directory.Packages.props`, в `csproj` идёт `PackageReference` без `Version`. `global.json` закрепляет **линейку** SDK, а не точную версию: `10.0.100` с `rollForward: latestFeature` берёт старшую установленную 10.0.x. Точную версию сюда не ставить — на машинах разработки SDK разные, и точное закрепление ломает сборку везде, кроме одной.

## Архитектура

| Проект | Что внутри | Зависит от Windows |
| --- | --- | --- |
| `PsDoctor.Core` | модель файла шоу, правила, диагнозы, арифметика; факты, журнал сеанса, контракт API, разбор сценариев | нет |
| `PsDoctor.Infrastructure` | файлы, кодировки, процессы, Win32, ffmpeg; запуск программы под заданием, окна, действия сценария | да |
| `PsDoctor.Cli` | прогон и отчёт без интерфейса; подкоманда `observe` — команды наблюдателю | нет |
| `PsDoctor.Observer` | наблюдатель: Kestrel, маршруты, сеанс наблюдения | да |
| `PsDoctor.Observer.Client` | типизированный доступ к API наблюдателя | нет |
| `PsDoctor.Workbench` | Avalonia: пульт владельца — сценарии, лента фактов, диалоги стенда | нет |
| `PsDoctor.App` | Avalonia: отчёт, одна кнопка, трей — пока каркас Э0 | да |

Граница не вкусовая: в `Core` не попадает ничего, что открывает файл, спрашивает операционную систему или знает про время. Разбор работает над текстом, а не над путём; всё остальное уходит в `Infrastructure`.

**У каждого проекта свой `README.md` рядом с кодом**: назначение, граница, с чего читать, чего в нём нет. Он отвечает на то, чего в коде не видно, и **не пересказывает код**: списки маршрутов, видов фактов и команд туда не выносятся — их даёт `grep` за минуту, а в документе они только устаревают. Правило правки одно: README проекта правится **тем же коммитом**, который двигает границу проекта, и не трогается, когда граница на месте. Отдельного прохода «актуализировать документацию» не заводится.

Документы разной скорости устаревания не смешиваются: решения и причины — в `docs/`, карта кода — в README рядом с кодом, разбор состояния на дату — снимок в закрытой памяти, который не актуализируется никогда.

**Кодировка — единственная дверь.** Кириллица внутри `.psh` записана в CP1251, а этой кодовой страницы в .NET нет без регистрации провайдера. Регистрация сделана один раз в `ShowFileEncoding`, и открывать файл шоу мимо него нельзя: иначе пути читаются как мусор и живые файлы объявляются потерянными.

**CLI раньше интерфейса.** Разбор файла и арифметика по нему не нуждаются в Windows и отлаживаются на машине разработки; интерфейсу без работающего ядра показывать нечего.

**Три процесса** — служба, трей и зонд — это предложение в [docs/architecture.md](docs/architecture.md), а не существующий код. Причина разделения: докторов трей обязан быть надёжным, а трассировка и работа с чужими процессами — именно то, что падает. Практика это предложение уже поправила: чтение окон из службы невозможно, см. ниже.

**Наблюдатель — второй продукт в том же решении.** Долгоживущий процесс в сеансе пользователя на стенде: запускает ProShow под заданием Windows, видит куст его процессов и окна, выполняет короткие сценарии (`launch`, `press`, `render`, `close` и ожидания) и отдаёт поток фактов по HTTP с ключом Bearer. Вердиктов не выносит: факт — это номер, время, вид и числа, слов в нём нет. Клиентов у API может быть сколько угодно; сегодня живой один — `psdoctor observe`, которым пользуется агент. Устройство — в [docs/architecture.md](docs/architecture.md), состав и критерий — [Э4.0](docs/plan.md), стенд — [docs/lab.md](docs/lab.md).

**Три правила формата, на которых стоит разбор.** Ключи плоские, с индексами в пути (`cell[1].images[3].keyframes[0].zoomX`), и режутся по **первому** знаку равенства. Ключ пишется только когда значение неумолчальное, поэтому модель отличает «не задано» от «ноль»; единственное доказанное умолчание — счётчики, и они умолчаются в ноль. Счётчик авторитетнее набора: элемент, у которого всё умолчальное, не записывается целиком, так что «объявлено больше, чем разобрано» — норма. Подробности в [docs/psh-format.md](docs/psh-format.md).

**Незнакомый ключ — данные, а не ошибка.** Доктор читает малую часть формата (около 90 форм из 400) и должен об этом знать: всё прочее ложится в словарь форм и видно в отчёте. Парсер не бросает исключений на содержимое вообще — продукт существует ради сломанных проектов.

**Разрешений картинок в файле шоу нет.** Главное число продукта — сумма распакованных пикселей — снимается чтением заголовков медиафайлов (PNG, JPEG, PSD, свои читалки в `Infrastructure`). Видео опознаётся, но не измеряется, и в отчёте так и сказано: «не опрашивали», а не «неизвестно».

**Правила приёмки — данные, а не константы.** Каждое правило это класс с устойчивым идентификатором, уровнем исполнения и уверенностью из карточки [docs/diagnostics.md](docs/diagnostics.md). Находка — правило плюс **конкретный объект** с адресом, переживающим правку проекта, и числами, на которых правило сработало. Человеческих фраз в находке нет: слова живут в окне.

**Порогов нет ни у одного правила, и это не недоделка.** Правило считается всегда и пишет срабатывания; код возврата 1 дают только находки, прошедшие порог, поэтому пока исход всегда 0. Числа для порогов набираются работой. Не придумывать пороги самостоятельно.

Этапы Э0–Э7 и числовые критерии готовности — в [docs/plan.md](docs/plan.md). Сделаны Э0 (каркас), Э1 (разбор, инвентарь, машинный отчёт) и Э2 (шесть правил приёмки); идёт Э4.0 (наблюдатель): шаги Ш0–Ш3 и `render` сданы с числами; Ш5 (пульт) сдан с числами, кроме тестов на стенде; код Ш4 (гигиена сеанса) в репозитории, но таблица прогона в плане ещё не заполнена. Критерии привязаны к боевым проектам и заново не придумываются; у каждого сделанного этапа в плане таблица с числами.

Что удалось выяснить про чужой формат и чужую программу по ходу работы — в [docs/reversing/](docs/reversing/README.md), опыты с датами — в [журнале](docs/reversing/journal.md). Установленный факт переезжает оттуда в `docs/psh-format.md`; догадка остаётся в журнале.

## Ход работы

**Оснастка опытов — не архитектура, и это помечено в коде.** Всё в `lab/` — обвязка стенда, в поставку не едет ни строки. Первая строка каждого скрипта называет его вид: `Оснастка стенда` (живёт постоянно), `Цикл опыта` (живёт, пока живёт пункт критерия), `Зонд опыта` (одноразовый, после ответа удаляется, а ответ уезжает в журнал реверсинга). Подробности — [lab/README.md](lab/README.md). Зонд не чинят и не развивают: написанный под один вопрос в один день, он врёт на следующей версии программы.

Работа разнесена по чатам: один планирует и фиксирует ход, остальные делают — этап или мелкую доработку. У чата-исполнителя нет ничего, кроме этих документов: он не слышал обсуждения и не помнит раунда проектирования. Поэтому раздел этапа в плане — не заметка о замысле, а единственный вход в работу.

**Раздел этапа годен к передаче, когда в нём есть четыре вещи:** состав — что входит; граница — что не входит и почему; критерий, проверяемый числом или командой; ссылки на решения, на которых этап стоит. Критерий, требующий того, чего на этапе нет, — не критерий: Э2 требовал назвать разнобой частот кадров, а частоты кадров в файле шоу нет вовсе, и работа упёрлась в это на первом шаге. Образцы того, как выглядит годный раздел, — Э1 и Э2 в [docs/plan.md](docs/plan.md).

**Кто что правит.** Чат-исполнитель дописывает **только свой** раздел плана: пометку «сделано» и таблицу чисел из прогона. Всё остальное в плане принадлежит чату планирования — состав будущих этапов, порядок, раздел «чего в плане нет». Мелкие доработки в план не попадают вовсе, им место в [docs/chores.md](docs/chores.md).

**Сначала накопанное.** До того как предлагать опыт, поиск или инструмент, — поиск по `Memorex/memory/`, `docs/reversing/journal.md` и `Memorex/actions/open.md`, и первой строкой сказать, что там уже есть. 16.09.2026 полдня ушло на обход диалогов программы, хотя ключ `-nowarnings` был найден в её модулях тем же утром и записан.

**Числа берутся из прогона, а не из рассуждения.** Профиль по одному проекту — наблюдение, и пачка его регулярно опровергает. Чат планирования код не запускает, поэтому число, которого прогон не дал, в критерий не ставится: ставится способ его получить.

Коммит готовит тот чат, который делал работу, по правилам раздела «Разделение работы». Явный запрос владельца уже является разрешением; повторный вопрос не нужен.

## Чужой материал

Доктор проверяется на настоящих проектах, и они в репозиторий не попадают.

- `inbound/` — двор пациентов: папка на проект, как пришло. Содержимое не версионируется, `.gitignore` пропускает в историю только `inbound/README.md`.
- Боевые файлы в тесты не копируются: `BattleProject` ищет их **и в `Memorex/sources/`, и в `inbound/`** сам, а когда материала нет — тесты молча не выполняются.
- Пропуски разделены по причинам: у проекта из закрытой памяти медиа рядом нет, у проекта из двора есть, и тест на разбор пропускается отдельно от теста на сумму пикселей. Иначе весь боевой блок замолчал бы целиком и никто бы этого не заметил.
- **Числа конкретного проекта лежат файлом `ожидаемое.json` рядом с ним**, а не в коде теста: имена проектов содержат названия клиентских работ. В сообщениях тестов проект зовётся номером, а не именем. Там же раздел `находок` — сколько раз сработало каждое правило.
- Проектов во дворе уже семь, версий программы в них четыре. Профиль по одному файлу это наблюдение, а не закон, и пачка это регулярно подтверждает: на двух проектах казалось, что слои переходов не несут файлов, на семи оказалось, что несут.
- Двор откалиброван не везде. Числа в `ожидаемое.json` сняты на одной машине, и на другой рядом с проектами их может не быть. Строгость задаёт метка `inbound/.calibrated`: где она лежит, пропажа всех ожидаемых чисел — поломка; где нет — такие тесты не выполняются. Метка, как и всё во дворе, не версионируется: это свойство машины.
- **Хранилище владельца** — большая выборка файлов шоу вне репозитория, медиа рядом с каждым. Есть не на каждой машине, путь у каждой свой — он записан в `AGENTS.local.md`. **Только чтение: в хранилище не пишется ничего, включая временные файлы и результаты.** Материал не проверен — часть проектов может быть сломана, и видно это только в самой программе, поэтому большинство в нём не доказывает нормы. Условия работы с ним — в разделе [Э2.1](docs/plan.md).

## Memorex — внутренняя память проекта

`Memorex/` это **отдельный закрытый репозиторий** (`github.com/qSerj/DoctorMemorex`), лежащий внутри рабочего каталога и исключённый из истории проекта через `.gitignore`. В нём разборы реальных проектов, замеры, отвергнутые решения и дословные слова владельца — то, чему не место в открытой документации.

У памяти свои правила, и они записаны в `Memorex/CLAUDE.md`. Обращаться к памяти только по ним: прочитать их перед работой с памятью, а не догадываться. Эти правила не менять и не считать инструкцией по разработке проекта — они про хранилище, а не про код.

Что из соседства следует здесь:

- Коммиты памяти делаются изнутри `Memorex/`, коммиты проекта — из корня. Путать нельзя.
- Правила локальных коммитов памяти относятся только к `DoctorMemorex`. Для открытого проекта действуют его собственные правила. Fetch/pull/push в обоих репозиториях выполняет владелец согласно договору 21.09.2026; файлы правил Memorex при этом не меняются.
- Памяти нет на чистой машине: владелец выполняет `git clone git@github.com:qSerj/DoctorMemorex.git Memorex` из корня проекта. Особенности SSH на Windows — в [docs/environments.md](docs/environments.md).

## Окружения и локальный файл

Разработка идёт на разных машинах, и возможности у них разные: под Linux — разбор, правила, CLI и тесты; под Windows — ещё и интерфейс, процессы, реестр, живая программа. Что где делается и чего где нет — [docs/environments.md](docs/environments.md). Задача, требующая того, чего на текущей машине нет, не имитируется: называется, чего не хватает, и откладывается до подходящей машины.

**Всё, что относится к конкретной машине, живёт в `AGENTS.local.md`**, а не здесь: пути к хранилищу и ProShow, установленные инструменты, откалиброван ли двор, особенности оболочки. Файл не версионируется; шаблон — [AGENTS.local.md.example](AGENTS.local.md.example). Если его нет — считать, что особых возможностей у машины нет, и спросить, а не угадывать пути.

## Документы

Карта — [docs/README.md](docs/README.md). У каждого раздела есть статус: **Согласовано**, **Предложение**, **Требует проверки**, **Открыто**. Предложение не превращается в требование без явного решения владельца. Решение хранится в профильном документе, в остальных местах на него ссылаются; закрытый вопрос переносится из [docs/open-questions.md](docs/open-questions.md) в документ по теме.

Проектирование ведётся раундами в `design/`: `initial/` заморожен и не правится, текущий раунд — `tier1/`. Решение, отменяющее сказанное в намётках, записывается документом текущего раунда, а не правкой старого.
