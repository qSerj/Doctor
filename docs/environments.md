# Окружения разработки

Статус: **Согласовано**, 16.09.2026.

Разработка идёт на разных машинах, и это нормальное состояние, а не временное. Возможности у машин разные, и граница между ними проходит по тому, что нужно конкретной задаче: разбору файла шоу Windows не нужна, наблюдению за живой программой — нужна.

Всё, что относится к одной конкретной машине — пути, инструменты, оболочка, откалиброван ли двор, — записано в её `AGENTS.local.md`. Файл не версионируется, шаблон лежит в корне: `AGENTS.local.md.example`. В этом документе — только то, что верно для любой машины своего типа.

## Что где делается

| Работа | Linux | Windows | Windows с ProShow |
| --- | --- | --- | --- |
| Сборка и тесты `Core`, `Infrastructure`, `Cli` | да | да | да |
| Разбор файлов шоу, правила приёмки, машинный отчёт | да | да | да |
| Прогон по двору и хранилищу | если материал лежит на машине | так же | так же |
| Сборка `App` | да | да | да |
| Осмысленный запуск `App`: трей, служба, уведомления | нет | да | да |
| Сборка `Observer` и `Observer.Client`, тесты API и клиента | да | да | да |
| Процессы, Job Object, ETW, реестр | нет | да | да |
| Тесты с Win32: задание, процессы, окна | нет | да | да |
| Работающий наблюдатель: запуск программы, окна, сценарии | нет | нет | да |
| Проверка гипотез о самой программе: загрузка, рендер, кэш | нет | нет | да |
| Подтверждение, что проект вообще открывается | нет | нет | да |

Задача, которой нужно то, чего на машине нет, не имитируется. Называется, чего не хватает, и она откладывается до подходящей машины. Особенно это касается утверждений о поведении программы: сделанные без неё, они остаются догадками и пишутся в журнал реверсинга, а не в формат.

## Linux

Машина разработки ядра. Здесь делается всё, что работает над текстом и числами: разбор, модель, правила, CLI, тесты.

Материала здесь обычно меньше, чем на машине, где снимались числа. Поэтому тесты, сверяющие ожидаемые числа, выполняются только на откалиброванном дворе — там, где лежит метка `inbound/.calibrated`, — а без неё молча пропускаются. Это не ослабление тестов: без метки нечего сверять, и падение означало бы только «машина не та».

## Windows

Всё, что на Linux, плюс то, ради чего продукт существует: интерфейс, трей, служба, процессы, трассировка, реестр.

**SSH и память.** Закрытая память клонируется по SSH. Делать это из PowerShell, где `git` берёт системный OpenSSH: `ssh` из Git Bash не видит ssh-agent Windows и даёт `Permission denied (publickey)`.

**Кодировка консоли.** Отчёт CLI — JSON в UTF-8. При разборе вывода в PowerShell кодировку консоли выставлять явно, иначе кириллица в путях читается как мусор ещё до того, как дойдёт до доктора.

## Windows с ProShow

Единственное место, где можно проверить утверждения о самой программе: грузится ли проект, как долго, падает ли рендер, что происходит с кэшем. Без неё доктор умеет считать, но не умеет доказывать, что посчитанное связано с глюками.

Владелец 16.09.2026 решил завести такую машину виртуальной: Windows с установленным ProShow и отдельным диском большой ёмкости под выборку проектов для исследования.

Что из этого следует для работы:

- выборка на отдельном диске — это хранилище в смысле [Э2.1](plan.md): только чтение, путь в `AGENTS.local.md` виртуальной машины;
- у виртуальной машины своё железо и свой масштаб экрана, поэтому замеры времени загрузки с неё не переносятся на рабочую машину монтажёра как есть — сравнивать можно только прогоны на одной машине между собой;
- снимок виртуальной машины до опыта с кэшем или правкой проекта — дешёвая страховка, которой на рабочей машине нет.

С 16.09.2026 машина живёт в VirtualBox и служит стендом [лаборатории](lab.md). По договору 21.09.2026 опыты запускает владелец, агент готовит их код и анализирует результаты.

С Э4.0 на ней же живёт [наблюдатель](architecture.md): процесс в сеансе пользователя, поднимаемый задачей планировщика. Из этого следует правило для тестов: зелёный `dotnet test` на Linux о Win32-части не говорит **ничего** — задание, процессы и окна проверяет владелец на стенде, запуская `lab/observer.sh`. Тесты процессов идут по SSH в нулевом сеансе, тесты окон — задачей в сеансе пользователя.
