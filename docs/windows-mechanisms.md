# Механизмы Windows

Статус: **Предложение**. Владелец 15.09.2026 снял ограничения: «Он может какие угодно фокусы использовать, дадим ему администраторские привелегии, открывать процессы, подцепляться к ним, читать, хуки, наблюдение. Если что - запускать уместные (нужные) тулсы для слишком хитрых системных дел».

Ограничения сняты, но выбор остаётся. Ниже — чем пользоваться и в каком порядке.

## Порядок предпочтения

1. **Документированный Windows API.** Дёшево, стабильно, не ломается от обновлений.
2. **ETW** — штатная трассировка. Даёт то, ради чего иначе понадобился бы свой драйвер.
3. **Внешние утилиты**, уже стоящие на машине. Никогда не тянутся молча.
4. **Недокументированное и инъекции.** Средство последней надежды.

Правило простое: подниматься на ступень выше можно, только когда ступенью ниже задача не решается. Каждое применение третьей и четвёртой ступени записывается в журнал вместе с причиной.

## ETW

Event Tracing for Windows — механизм самой операционной системы, встроенный в неё с начала двухтысячных. Не продукт стороннего производителя, хотя на машине разработчика он чаще всего появляется вместе с чужими профилировщиками: JetBrains ставит собственную службу-сборщик ETW вместе со своими инструментами, чтобы не поднимать права на каждую трассировку.

Что даёт здесь: ядерный провайдер `FileIo` отдаёт поток событий «процесс открыл, прочитал, закрыл вот этот файл». Это ровно та картина, которая была увидена глазами при наблюдении зависания, только без интерфейса и без собственного драйвера файловой системы.

Из .NET — библиотека `TraceEvent`, та же, на которой построен PerfView.

Цена: нужны права администратора, и объём событий велик — сессию обязательно сужать до конкретного процесса, иначе трассировка сама станет нагрузкой.

**Следствие для плана.** Вопрос «чем узнавать, какой файл процесс читает прямо сейчас» стоял открытым, потому что документированного способа перечислить открытые хэндлы нет, а недокументированный трогать не хотелось. С правами администратора ответ — ETW, и недокументированное не нужно вовсе.

## Работа с процессами

`OpenProcess` и далее по документированному набору: счётчики ввода-вывода, процессорное время, рабочее множество, признак незанятой очереди сообщений у главного окна. Чтение чужой памяти — `ReadProcessMemory` — только на чтение и без последствий для наблюдаемого.

Job Object для запущенного из-под доктора процесса: даёт всё потомство надёжно, а не поиском по имени. **Ограничение `kill on job close` снимается явно**, иначе выход доктора убьёт чужую работу.

**Программа открывает проект аргументом командной строки, DDE нет** — проверено 16.09.2026 на версии 9.0.3797, [журнал](reversing/journal.md). В реестре `shell\open\command` = `"…\proshow.exe" "%1"`, ветки `ddeexec` нет, пользовательского переназначения нет; путь программа приняла и проект открыла. Это был гейт Э3, и он закрыт: запасной путь «сопровождение с ручным открытием» не нужен. Строка запуска всё равно читается из реестра, а не пишется в коде: у другой установки она может быть своей.

## Инъекции и хуки

Технически доступны, разрешение получено. Тем не менее в план не входят, и вот почему.

Целевой процесс 32-битный — хук потребует отдельной 32-битной библиотеки. Внедрение кода в чужое приложение способно уронить ровно тот процесс, который мы пытаемся спасти. И происходит это в день сдачи, когда цена падения максимальна.

Чтение процесса снаружи даёт почти столько же и не трогает его вовсе. Инъекция остаётся средством последней надежды: если окажется, что без неё не ответить на важный вопрос, решение принимается отдельно и записывается сюда.

## Внешние утилиты

Допустимы. Три условия.

Ничего не скачивается и не устанавливается молча: инструмент либо уже есть на машине, либо его ставит владелец осознанно.

Отсутствие инструмента не ломает доктора. Нет утилиты — соответствующая проверка просто не выполняется, а остальное работает.

Каждый вызов записан в журнал: что запущено, зачем, что ответило. Иначе через полгода никто не восстановит, откуда взялся вывод.

## Права

Права администратора берутся **один раз, при установке службы**, и дальше не запрашиваются никогда. Это и есть причина выбрать службу вместо повышенного приложения: иначе окно UAC всплывало бы при каждом запуске, и человек привык бы нажимать «да» не читая.
