# Лаборатория

Статус: **Согласовано**, 16.09.2026.

Стенд, на котором агент сам ставит опыты над живой программой: откатывает виртуальную машину к снимку, запускает ProShow, ведёт его интерфейс, собирает наблюдения и забирает результат, — без человека у компьютера.

## Зачем

Опыты, записанные в [журнале реверсинга](reversing/journal.md), уже устроены как лаборатория: скрипт пишется на машине разработки, выполняется в виртуальной машине, результат возвращается через общую папку. Но выполняет и ждёт человек. Этого хватает на один прогон и не хватает на двадцать.

А двадцать нужны. Сбои программы неповторяемы: тот же рендер падает дважды и проходит с третьего раза. Такой сбой ловится только числом прогонов из известного состояния, и руками его не поймать.

Вторая причина — дальняя. Программу можно не реверсить до исходного кода, а превратить в **экспериментально доступную спецификацию её собственного поведения**: менять вход, смотреть выход, записывать правило. Стенд для этого тот же, что для доктора, поэтому строится один раз.

## Устройство

```text
Linux (машина разработки)
├── агент
├── VBoxManage — снимки, запуск, остановка
├── ffmpeg — сравнение кадров
└── Ghidra headless — позже
        │ host-only сеть, общая папка
        ▼
Windows 10 в VirtualBox — расходный стенд
├── ProShow и кодеки как на рабочей машине
├── «руки»: MCP-сервер в сеансе пользователя — UI Automation, скриншоты, клавиатура и мышь
├── SSH по ключу — файлы, процессы, реестр
└── Sysinternals, позже x32dbg
```

Мозг остаётся на Linux, Windows — внешняя система, которую агент исследует. Виртуальная машина расходный материал: испорченная опытом система откатывается к снимку.

## Решения и их причины

**VirtualBox.** Всё управление машиной — в `VBoxManage`. Принципиальной разницы с VMware для стенда нет: агент работает в основном с Windows внутри, а не с гипервизором.

**Windows 10, а не 11.** Замеры и поведение должны совпадать с рабочей машиной монтажёра, а не быть современнее её.

**«Руки» — готовый MCP-сервер, а не своя разработка.** Какой именно — выбирается осмотром вариантов. Требования: работает в сеансе вошедшего пользователя, отдаёт дерево UI Automation и скриншоты, нажимает и вводит.

**Сервер стартует при входе пользователя, Windows входит сама.** Процесс, запущенный через SSH или службой, рабочего стола не видит: окна программы живут в интерактивном сеансе. SSH поэтому служит для файлов, процессов и реестра, а не для интерфейса.

**Скриншоты — второй основной путь, а не запасной.** Опытом установлено, что UI Automation читает у ProShow диалоги, заголовок окна с именем проекта и кнопки, но не строку прогресса. Временная шкала и превью, скорее всего, нарисованы самой программой.

**Базовый снимок снимается с запущенной системой.** Откат тогда занимает секунды, а не загрузку Windows, и «руки» уже работают.

**Паролей нет.** `VBoxManage guestcontrol`, как и `vmrun runProgramInGuest`, требует имя и пароль гостевой учётной записи — не используется. Вход в гостевую систему — SSH по ключу, ключ прописывает владелец.

**Сеть только host-only.** Сервер, выполняющий команды, — полный доступ к машине, наружу он не смотрит. Самой программе сеть не нужна.

**32 бита.** `proshow.exe` 32-битный, поэтому отладчик — x32dbg, а не x64dbg.

## Оракул

У ProShow вход и выход измеримы целиком: вход — файл шоу и медиа, выход — видео. Отсюда цикл:

1. Поменять в файле шоу один ключ.
2. Отрендерить.
3. Сравнить кадры с рендером исходного проекта.
4. Записать правило; установленное переезжает в [формат файла шоу](psh-format.md).

Разбор понимает около 90 форм ключей из примерно 400. Остальные учатся этим циклом, и правила приёмки получают опору на поведение программы, а не на догадку.

Два вопроса проверяются первыми, потому что от них зависит цена цикла:

- **Детерминирован ли рендер.** Один проект дважды; совпадают ли кадры побайтно. Если нет, сравнение идёт по метрике.
- **Можно ли без интерфейса.** Ключей рендера в командной строке нет, но есть `/thumbnail`. Если он отдаёт кадр шоу, это оракул без кликов; если нет, рендер ведут «руки».

## Этапы

Номер — имя, а не очередь, как в [плане](plan.md). Критерий каждого этапа проверяется прогоном без человека.

| Этап | Что | Готово, когда |
| --- | --- | --- |
| Л0. Стенд | ВМ с программой и кодеками, базовый снимок с запущенной системой, SSH по ключу, общая папка | агент с Linux откатывает машину, запускает команду в гостевой системе и забирает файл |
| Л1. Руки | MCP-сервер в сеансе пользователя | открыть проект, закрыть диалог старого формата, прочитать заголовок, закрыть программу — 10 раз подряд |
| Л2. Рендер | вывод видео через интерфейс программы до файла на Linux | рендер 4K-проекта из журнала повторён 5 раз |
| Л3. Оракул | детерминизм, мутация ключа, сравнение кадров | хотя бы одна непонятая форма ключа объяснена циклом |
| Л4. Сбои | Process Monitor и ETW, серия прогонов тяжёлого проекта | падения и удачи сравнены по пику памяти и по файлу, на котором встала программа |
| Л5. Статика | Ghidra headless на Linux: строки, импорты, модули | карта модулей и функций, разбирающих ключи файла шоу |
| Л6. Отладчик | x32dbg с автоматизацией | действие в интерфейсе привязано к функции программы |

Л0–Л2 закрывают нужды доктора: без них не проверить ни одно лечение и не поймать ни один неповторяемый сбой. С Л3 начинается дальняя цель.

## Чего здесь нет

- Параллельных клонов. Одна машина, пока серия прогонов не упрётся во время.
- Wireshark, API Monitor и прочего «музея инструментов». Добавляется, когда опыт потребует.
- Своего оркестратора над агентом. Сверху агент, снизу инструменты, между ними ничего.
- Скриптов опытов с названиями проектов. Скрипты живут в репозитории, проект указывается параметром.

## Ход работ

**Л0 — сделано, 16.09.2026.** Машина в VirtualBox, Windows 10 22H2, снимок с запущенной системой, SSH по ключу. Цикл «выключить → откатить → запустить → команда в гостевой системе → файл на Linux» пройден без человека; SSH отвечает через 1 с после старта. Первый запуск сразу после отката может упасть — машина ещё заблокирована, нужен повтор.

**Л1 — в работе.** «Руки» поставлены: Windows-MCP 0.8.5, запускается при входе пользователя, слушает только host-only адрес, пускает только хост и только с ключом; PowerShell, реестр и файлы в нём отключены — это делает SSH. С хоста видны дерево UI Automation и скриншоты, программа запускается с проектом, диалог старого формата ожидается и находится.

Первая попытка нажать «ОК» в этом диалоге не удалась, и причины две. Фокус был у панели задач: окно, запущенное программно, не получает права выйти на передний план, и нажатие клавиши уходит не туда. Курсор после перемещения оказывался не там, куда его ставили; подозревается интеграция мыши VirtualBox, которая передаёт гостю положение указателя хоста, — не проверено.

Дальше: проверить курсор при машине без окна или без интеграции мыши; нажимать через шаблон Invoke UI Automation, которому не нужны ни фокус, ни мышь, — скриптом в сеансе пользователя; выводить окно вперёд до нажатия.

**Л1, вторая попытка — критерий пройден скриптом, 16.09.2026.** Стенд перенесён на Windows-хост. Скрипт в сеансе пользователя (`lab/Invoke-LabUi.ps1` — задача планировщика, `lab/guest/Cycle-Uiamcp.ps1`) десять раз подряд открыл проект старого формата, закрыл диалог старого формата и диалог о недостающем шрифте, прочитал заголовок и закрыл программу — без человека и без модели, курсор не сдвинулся ни разу. Нажатие — `action invoke` CLI [mcp-server-uiautomation](https://github.com/trsdn/mcp-server-uiautomation) по описанию кнопки; работает и в неактивном диалоге. Что при этом выяснилось о диалогах и деревьях UI Automation — в журнале реверсинга и в закрытой памяти.

Проверено попутно и не пригодилось: .NET-клиент UI Automation в Windows PowerShell 5.1 видит кнопки программы панелями без Invoke; Terminator как «руки» отвергнут — сценарии YAML в выпуске 0.24.32 не разбираются, CLI не умеет ключ авторизации. После отката к снимку SSH на этом хосте отвечает через 4 минуты — причина не выяснена, для серий прогонов это препятствие.

**Решение владельца 16.09.2026: автоматизация интерфейса откладывается.** Кнопки на стенде нажимает владелец; первым делается наблюдатель доктора, который пишет, что программа при этом делает, — этап «Э4.0. Наблюдатель v0» в [плане](plan.md). Л2–Л6 остаются в силе, но идут после него, из накопленного.
