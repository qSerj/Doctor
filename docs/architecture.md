# Архитектура

## Стек

Статус: **Согласовано**.

.NET 10, C#, Avalonia. Версия SDK закреплена в `global.json`, версии пакетов — централизованно в `Directory.Packages.props`, общие свойства сборки — в `Directory.Build.props` с `TreatWarningsAsErrors`.

Avalonia, а не WPF. Причина не в кроссплатформенности: продукт Windows-only. Причина в том, что WPF навсегда закрывает возможность общего кода с соседним проектом того же владельца, а Avalonia оставляет её открытой.

## Слои

Семь проектов кода и пять тестовых. Таблица приведена в соответствие с решением по состоянию на 18.09.2026: до Э4.0 проектов было четыре.

| Проект | Содержимое | Зависит от Windows |
| --- | --- | --- |
| `PsDoctor.Core` | модель файла шоу, правила, диагнозы, арифметика; записи фактов, журнал сеанса, контракт API и разбор сценариев | нет |
| `PsDoctor.Infrastructure` | файлы, кодировки, процессы, Win32, ffmpeg; запуск программы под заданием, опрос окон, действия сценария | да |
| `PsDoctor.Cli` | прогон и отчёт без интерфейса; подкоманда `observe` — команды наблюдателю | нет |
| `PsDoctor.Observer` | наблюдатель: хост Kestrel, маршруты, сеанс наблюдения | да |
| `PsDoctor.Observer.Client` | типизированный доступ к API наблюдателя; им пользуются CLI и пульт | нет |
| `PsDoctor.Workbench` | Avalonia: лаборатория инженера — сценарии, опыты, лента фактов, диалоги, пакеты; подключается к любому Observer | нет |
| `PsDoctor.App` | Avalonia: Doctor монтажёра — окно, трей, проверка проекта, мастер «Решить проблему», наблюдение через Observer.Client | да |

**Два продукта, а не один с двумя режимами.** Статус: **Решено** раундом [tier2](../design/tier2/roles.md), 23.09.2026. `PsDoctor.App` — Doctor монтажёра: самостоятельное приложение для человека без технической подготовки, удобство и понятность во главе угла. Он **применяет готовые рецепты**: осматривает проект, узнаёт известную проблему и даёт совет с понятным действием; неизвестное — не его дело. `PsDoctor.Workbench` — лаборатория инженера: опыты, поиск паттернов, разбор журналов, пакеты для агента. Рецепты создают инженер и агент на Workbench и стенде; App их только применяет. Подробный вид tier1 для администратора — это Workbench, а не второй режим окна App.

Workbench сдан 18.09.2026 шагом Ш5 [Э4.0](plan.md): решение «пульт и агент — два клиента одного API» проверено обоими клиентами, и второй не повторил кода первого. Он безразличен к тому, к какой машине подключён: стенд и машина монтажёра для него одинаковы, опыты идут и там и там. Что App и Workbench умеют сейчас — их README и [снимок раунда](../design/tier2/baseline.md).

Workbench также собирает лабораторный пакет `exchange/checks/<id>`: исходный JSONL журнала, точный сценарий, выбранный изменившийся MP4 и контрольные суммы. Observer регистрирует только MP4, появившиеся или изменившиеся в каталоге проекта после `render`; произвольные пути для скачивания не принимаются. Сырой ETW добавляется по явному флажку.

Правило разделения простое: в `Core` не попадает ничего, что открывает файл, спрашивает операционную систему или знает про время. Разбор работает над текстом, а не над путём; исполнитель сценария получает канал сигналов, а часы остаются снаружи — время приходит тиком от сеанса.

Шов держится: `Core` не ссылается ни на один пакет, `Infrastructure` — только на `System.Diagnostics.EventLog`. По нему тесты обходятся без Windows и без файлов.

**Одно исключение из правила названо явно.** В `Core/Observation/ProgramFacts.cs` лежат `ProShowWindows` — заголовки окон ProShow и номер пункта меню рендера: ожидание `wait render-done` сравнивает заголовок, а ожидания живут в ядре. Знание о чужой программе в ядре — это долг, а не образец. Следующее правило такого рода выносит имена окон в данные сеанса, а не добавляет к этому списку.

## Почему CLI появляется раньше интерфейса

Статус: **Согласовано**.

Весь первый этап — разбор файла шоу и арифметика по нему — не нуждается в Windows вообще и отлаживается на машине разработки. Интерфейс без работающего ядра показывать нечего, а ядро без интерфейса уже приносит отчёт.

Важная оговорка, появившаяся в раунде: отчёт CLI **машинный** ([cli.md](../design/tier1/cli.md)). Довод «CLI приносит отчёт раньше интерфейса» поэтому означает «раньше приносит числа», а не «раньше говорит с человеком». Слова живут только в окне, и второй копии формулировок не заводится — две копии однажды разойдутся.

Побочная польза: CLI остаётся навсегда как инструмент владельца и как способ прогнать пачку проектов разом. Лечить он не умеет и в чужой каталог не пишет никогда: прогон пачки остаётся чистым чтением.

С Э4.0 у CLI появилась вторая роль: подкоманда `psdoctor observe` — это команды [наблюдателю](#наблюдатель) из оболочки, и ими пользуется агент. Роль отдельная во всём: свой набор команд (`health`, `run`, `attach`, `sessions`, `facts`, `raw`, `cancel`, `confirm`, `dialogs`, `stop`), своя таблица кодов возврата — 0 выполнено, 1 сценарий не выполнен, 2 отказ наблюдателя, 3 сбой окружения, — и своя строка вывода: факты в stdout как есть, JSON Lines. Коды приёмочного прогона (0, 1, 2, 3 в другом смысле) к ней не относятся: это две разные команды под одним именем, и путать их таблицы нельзя.

## Наблюдатель

Статус: **Согласовано**, решение владельца 17.09.2026. Состав, границы и критерий — [Э4.0](plan.md); здесь только устройство и то, что из него следует для остальной системы.

Наблюдатель — **долгоживущий процесс с сетевым API**, а не команда CLI. С ним разговаривают трое — App монтажёра, Workbench инженера и агент из оболочки, — и это один и тот же API. App из сценариев использует только запуск и подключение; `press`, `render`, `close` не посылает никогда. Он запускает ProShow под заданием Windows, видит куст его процессов и окон, выполняет короткие сценарии и отдаёт поток фактов. Вердиктов он не выносит: «завис» и «норма» — не его слова.

**Он живёт в сеансе пользователя, а не в службе.** Служба работает в нулевом сеансе и окон программы не видит, а окна и диалоги — половина фактов. На стенде процесс поднимается задачей планировщика при входе пользователя, без повышения прав. Поэтому службы в продукте нет вовсе — см. [разделение процессов](#надёжность-и-разделение-процессов): чтение окон остаётся за процессом в сеансе пользователя навсегда, потому что причина не в удобстве, а в устройстве Windows.

**Факт — единица всего.** Одна запись JSON: номер по порядку в сеансе, время от старта, сеанс, процесс, вид (`kind`), данные. Слов в факте нет, как и в отчёте приёмки. Новый вид наблюдения — новая строка `kind`, а не новая версия протокола: файловый ввод-вывод [Э4.2](plan.md) ложится сюда же.

**Журнал сеанса пишется на диск** самим наблюдателем, JSON Lines, в его каталог в профиле пользователя. Поток — окно в этот журнал, а не единственная копия: клиент, отвалившийся посреди сеанса, переподключается с номера последнего факта и ничего не теряет. Правило «доктор в файлы не пишет» к наблюдателю не относится — это другой процесс с другой ролью, и пишет он себе, а не в каталог проекта.

**Протокол.** HTTP на Kestrel; команды — JSON, поток фактов — Server-Sent Events с фильтром по виду и номером, с которого начать. Слушает `127.0.0.1`, пока сетевой адрес не задан ключом `--listen`; не-петлевой адрес открывается только вместе с `--allow-remote` — TLS у протокола нет, и ключ едет по сети открытым текстом. Ключ Bearer обязателен всегда, открытых маршрутов нет, сверка ключа — постоянным временем. Имена отказов устойчивые (`program-running`, `bad-scenario`, `no-session`), а не фразы.

**Сценарий** — текст, строка на шаг, без переменных, ветвлений и циклов: `launch`, `press`, `close`, `render`, ожидания `wait title | dialog | exit | idle | render-done`; строка с `#` в начале — описание. Действия знают только ProShow: универсальных щелчков по координатам нет и не будет — от универсального инструмента этап уходит намеренно. Сценарий останавливается на первом сорвавшемся шаге и на неожиданном диалоге; наугад не нажимается ничего. С Э4.5 опыт ведёт и человек: `say "<текст>"` — инструкция оператору фактом `operator-instruction`, `wait <секунды>` — пауза, `wait confirm [<таймаут>]` — ждать кнопки «Сделано», которая приходит маршрутом `POST /scenarios/confirm` и пишется фактом `operator-confirmed`. После `say` и до следующего действия окна — забота оператора и сценарий не останавливают. Пассивный сеанс принимает сценарий только из этих шагов и ожиданий; сценарий с действием отвергается целиком, до первого шага. Цикл опытов — поправить проект, прогнать, измерить, повторить — живёт на хосте, в `lab/*.sh`, и наблюдатель о нём не знает.

**Границы процессов держатся намеренно.** Задание создаётся без «завершить процессы при закрытии задания», а сам запуск — с отвязкой от чужого задания. Ни выход наблюдателя, ни остановка его задачи планировщика не уносят ProShow с собой; закреплено тестом.

**Всё однократно, и это выбор.** Один живой сеанс, один сценарий, одна программа, один стенд; запуск отказывает, если программа уже запущена — хоть наблюдателем, хоть мимо него, потому что второй экземпляр путает кэши и число процессов. Следствие для будущего: «прогнать десять проектов разом» — это десять стендов, а не десять сеансов.

**Наблюдатель — часть поставки.** Статус: **Решено** раундом [tier2](../design/tier2/roles.md), 23.09.2026. На машине монтажёра он устроен так же, как на стенде: процесс в сеансе пользователя и ETW-помощник с наивысшими правами, обоих ставит установщик, права администратора берутся один раз при установке. Отличие только в настройке: у монтажёра наблюдатель слушает loopback, и App говорит с ним через него; сеть открывается настройкой, когда инженер подключается из локальной сети. Отдельного «режима машины монтажёра» с запретами нет: от столкновения с её работой защищают отказ `launch` при запущенной программе и запрет команд в пассивном сеансе.

**Сторож.** Зависший или упавший наблюдатель замечает сторож, перезапускает его и пишет факт. Наблюдатель — дочерний процесс сторожа, а не своя задача планировщика: задач при входе две, сторож и помощник ETW ([установщик](../install/README.md)). Короткоживущий процесс на каждый сеанс не делается, пока зависания наблюдателя не подтвердятся на практике.

**Эпизоды.** Известный плохой паттерн распознаёт **детектор** — чистый код в `Core`: факты на входе, эпизод на выходе («крутит перечитывание файла X»); тестируется на Linux по записанным журналам. Выполняется детектор в наблюдателе, эпизод пишется в журнал обычным фактом и виден всем клиентам. Эпизод — не вердикт: он называет наблюдаемое повторение, а не причину сбоя. Фразу и кнопку к нему подбирает App; слова по-прежнему живут только там. Рецепт доезжает до App обновлением через установщик, пороги детектора — данные.

**Срок хранения.** Журналы и сырьё хранятся в пределах срока и объёма — что наступит раньше, старое удаляется первым; сеансы с эпизодами и сеансы, начатые мастером App, живут дольше. Числа — настройка установщика. Пакет сеанса для разбора делает только Workbench.

## Кодировка

Кириллица внутри файла шоу записана в CP1251. В .NET эта кодовая страница не доступна без регистрации `CodePagesEncodingProvider`; без неё пути читаются как мусор и живые файлы объявляются потерянными. Регистрация сделана один раз в `ShowFileEncoding`, и открывать файл шоу мимо него нельзя.

## Тесты и закрытый материал

Статус: **Предложение**.

Боевые проекты — чужая клиентская работа, они лежат во дворе (`inbound/`) и во внешней закрытой памяти проекта, а репозиторий открытый. Поэтому тесты устроены так:

- обычные тесты работают на синтетических данных, лежащих в репозитории;
- боевые тесты ищут настоящие файлы шоу и в закрытой памяти, и во дворе, и **молча не выполняются**, когда материала нет;
- имена боевых файлов в коде не записаны — они содержат названия клиентских работ; файлы ищутся по расширению;
- точные числа конкретного проекта лежат рядом с ним, в его же закрытом каталоге, а не в коде теста.

Пропуски разделены по причинам, а не свалены в один. У проекта из закрытой памяти рядом нет медиа, у проекта из двора есть; тест на разбор и тест на сумму пикселей поэтому пропускаются независимо. Иначе весь боевой блок замолчал бы целиком, и никто бы этого не заметил.

Проверка на одном проекте — наблюдение, а не закон. Второй проект сразу это подтвердил: он собран в другой версии программы, и в нём есть расширения, которых в первом не было.

Так граница цела, а золотой тест на реальном материале есть у того, у кого этот материал есть.

## Надёжность и разделение процессов

Статус: **Решено** раундом [tier2](../design/tier2/roles.md), 23.09.2026; заменяет предложение «служба, трей, зонд» 15.09.2026.

Требование владельца 15.09.2026: доктор не закрывается, при закрытии окна уходит в трей, и должен быть «абсолютно надёжен, насколько это можно представить». Оно конфликтует с разрешением пользоваться любыми механизмами Windows: трассировка и подключение к чужим процессам — именно то, что падает. Поэтому рискованное живёт не в процессе окна.

| Процесс | Права | Время жизни | Задача |
| --- | --- | --- | --- |
| App | обычный пользователь | сессия пользователя | окно, трей, осмотр проекта, мастер, разговор с человеком |
| Наблюдатель | обычный пользователь | с входа пользователя | сеансы, окна и процессы ProShow, журнал, детекторы, API |
| ETW-помощник | администратор, выданы при установке | с входа пользователя | трассировка; связь с наблюдателем файлами в каталоге сеансов |
| Сторож | обычный пользователь | с входа пользователя | запуск наблюдателя своим дочерним процессом и его перезапуск, если тот упал или не отвечает |

**Службы нет.** Служба живёт в нулевом сеансе и не видит окон, а окна и диалоги — половина фактов; это выяснил Э4.0. Права администратора нужны только трассировке, и их держит ETW-помощник — задача планировщика с наивысшими правами, поставленная один раз при установке.

**App намеренно не повышен в правах.** У процесса с повышенными правами перестаёт работать перетаскивание файлов из проводника, и доктор не смог бы принять брошенный мышкой файл шоу.

**Зонд** из прежнего предложения — короткоживущий процесс для рискованной операции — не делается, пока не найдётся операция, которой он нужен.

Какими механизмами Windows при этом пользоваться — в [отдельном документе](windows-mechanisms.md).

## Кто что пишет

Статус: **Решено** раундом [tier1](../design/tier1/revision.md), 2.15; уточнено [tier2](../design/tier2/roles.md), 23.09.2026.

**Писатель в каталоге проекта один — App.** Всё, что появляется у оператора, принадлежит оператору, а не системе, иначе он однажды не сможет это удалить. Сейчас App пишет туда только переименованный `.pxc` при быстром восстановлении. Правка файла шоу на месте, гит и папка доктора рядом с проектом из tier1 **под вопросом**: программная оптимизация проектов после первых прогонов владелец считает сомнительной; до пересмотра этого в коде нет.

**Наблюдатель и ETW-помощник пишут только себе** — журналы и сырьё в каталог сеансов в профиле пользователя — и в каталог проекта не пишут никогда. Файл `proshow.phd` в каталоге программы и его зеркало `VirtualStore` App переименовывает сам, прав администратора это не требует.

## Права

Статус: **Решено**; уточнено [tier2](../design/tier2/roles.md), 23.09.2026.

Права администратора берутся **один раз, при установке**: установщик ставит ETW-помощника задачей планировщика с наивысшими правами. Окна повышения прав на каждый сеанс нет, системных окон оператор не видит вовсе.

Формулировка «в момент действия, на конкретное действие» относится не к правам, а к **подтверждению**: перед действием над служебными файлами App своим окном показывает, что будет сделано.
