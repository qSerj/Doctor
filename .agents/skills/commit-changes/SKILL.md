# Коммит проекта

Включать по явному «комить», «сделай коммит» или равнозначному запросу. Повторно подтверждение того же коммита не спрашивать.

Перед staging прочитать `git status` и `git diff`, определить точные файлы задачи и убедиться, что чужие изменения не попадут в коммит. Уже занятый индекс не смешивать с этой работой: сообщить владельцу, какие staged-файлы обнаружены, и остановиться. Добавлять только точные разрешённые пути; не использовать `git add -A` и широкие маски.

Перед коммитом осмотреть применимые hooks, учитывая `core.hooksPath`. Если hook запускает build, tests или другую неразрешённую проверку либо его поведение не удалось установить, передать этот шаг владельцу; hook не отключать и не обходить. Build/tests, `fetch`, `pull`, `push`, `amend` и переписывание истории в обычный запрос коммита не входят.

После проверки staged diff создать только локальный коммит с сообщением на русском. Если состав или принадлежность изменения неясны, не угадывать: назвать конкретную неоднозначность владельцу.

В ответе сообщить hash и тему коммита, оставленные вне коммита изменения и фактическое состояние проверки. Не приписывать текущему коммиту результаты другой версии. Использовать эту проектную инструкцию вместо одноимённой личной; её helper не запускать без проверки соответствия текущим ограничениям.
