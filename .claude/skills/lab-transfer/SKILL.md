# Переезд между машинами через накопитель

Разработка идёт на двух машинах — Linux-машина разработки и Windows-хост дома, — а стенд лаборатории (виртуальная машина VirtualBox) один и ездит с ними на переносном накопителе. Раскладка каталогов везде одна, поэтому переезд — это не творчество, а два обратных друг другу списка действий: **сборка** перед уходом и **подъём** на другой машине.

Смысл всего процесса: **в гите живёт код и документы, в закрытой памяти — знание, на накопителе — только то, чего в них нет.** Виртуальная машина, ключи, журналы прогонов, незакоммиченная работа. Если что-то можно отправить в гит — отправляется в гит, а не кладётся на накопитель: там оно устареет и разойдётся с репозиторием.

Пути к накопителю, папке обмена, хранилищу проектов и ключам у каждой машины свои и записаны в `CLAUDE.local.md`. Прочитать оттуда, а не угадывать. Ниже пути Linux-машины как образец.

## Раскладка комплекта

```text
<накопитель>/transit/psdoctor-lab/
├── README.md                     как поднять стенд; сверху строка о последнем обновлении
├── vm/Win10 - ProShow - Rev/     папка машины VirtualBox целиком, со снимками
├── ssh/lab_ed25519               ключ SSH лаборатории
├── secrets/                      ключи наблюдателя и «рук»
├── claude-memory/                автопамять Claude Code
├── CLAUDE.local.md.<машина>      копия локального файла каждой машины
├── tools/                        retarget, setup, wps
└── работа/<дата>-<тема>/         результаты дня, которых нет в гите
    ├── ПРОЧТИ.md                 главное: состояние, что осталось, грабли
    ├── журналы-прогонов.tar.gz
    └── незакоммиченное: патч + архив новых файлов
```

## Что помнить всегда

- **Коммит в открытый репозиторий — только с разрешения владельца.** Закрытая память коммитится и отправляется сразу, без спроса.
- **Копирование и развёртывание — после явного «да» по конкретному плану.** Это касается и копий проектов на стенд, и заливки на накопитель, если владелец о ней не просил сам.
- **Имена клиентских проектов в открытый репозиторий не попадают.** В скриптах они приходят переменными (`SHOW_FILE`, `PROJECT_SOURCE`), на накопителе лежат под нейтральными именами каталогов.
- **Новые снимки виртуальной машины снимает владелец.** Откатывать к существующему снимку можно свободно, снимать и удалять — нет.
- **Хранилище проектов только на чтение.**

## А. Сборка перед уходом

1. **Сначала гит.** Спросить про коммит работы проекта; закрытую память записать, закоммитить и отправить сразу. В `ПРОЧТИ.md` потом честно написать, что закоммичено, а что нет.
2. **Выключить стенд штатно**, ACPI, а не выдёргиванием питания:
   ```bash
   VBoxManage controlvm "<машина>" acpipowerbutton   # и подождать VMState=poweroff
   ```
   Пока машина работает, копировать её нельзя: диски в несогласованном состоянии.
3. **Синхронизировать папку машины на накопитель.** Копировать только отличия — неизменные диски пропускаются по размеру и времени, и вместо часа выходит полминуты:
   ```bash
   rsync -rt --delete "$HOME/VirtualBox VMs/<машина>/" "<комплект>/vm/<машина>/"
   ```
   В Git Bash на Windows-хосте `rsync` отсутствует — там `sync_dir` из `lab/portable.sh` или `robocopy /MIR`.
4. **Сверить копию по sha256** — накопитель внешний, и молча испорченный файл дороже пяти минут проверки:
   ```bash
   cd "$HOME/VirtualBox VMs/<машина>" && find . -type f ! -path './Logs/*' -print0 | sort -z \
     | xargs -0 sha256sum > /tmp/vm.sha256
   cd "<комплект>/vm/<машина>" && sha256sum -c --quiet /tmp/vm.sha256
   ```
5. **Положить то, чего нет в гите**, в `работа/<дата>-<тема>/`:
   - незакоммиченное: `git diff > ш<N>-изменения.patch`, новые файлы — `git ls-files --others --exclude-standard -z | tar --null -T - -czf ш<N>-новые-файлы.tar.gz`, и рядом `git rev-parse HEAD` в `на-коммите.txt`;
   - журналы прогонов из `artifacts/` (в гит они не идут);
   - образцы вывода, если по ним потом сверяются числа;
   - проект, которого нет в хранилище (например, пересохранённый на стенде), — иначе циклы нечем кормить.
6. **Обновить в комплекте** `secrets/`, `claude-memory/`, `CLAUDE.local.md.<эта машина>` и строку о дате обновления в начале `README.md`.
7. **Написать `ПРОЧТИ.md`** по шаблону ниже. Это главный файл переезда: другая машина начинает с него.

## Б. Подъём на другой машине

1. **Прочитать `работа/<последняя дата>/ПРОЧТИ.md` и `README.md`** комплекта и первой строкой сказать владельцу, что там: что сделано, что осталось, на каких коммитах репозитории.
2. **Забрать гит:** `git fetch`, сравнить с локальным. Если здесь остался черновик, который на той машине уже доработан и закоммичен, — спрятать его `git stash push -u -m "<что это>"` и `git pull --ff-only`, а не разбирать конфликты руками. Копия черновика всё равно лежит на накопителе.
3. **Виртуальная машина.** Порядок важен: пока машина зарегистрирована, подменять её файлы нельзя.
   ```bash
   VBoxManage unregistervm "<машина>"                 # без --delete: файлы остаются
   rsync -rt --delete "<комплект>/vm/<машина>/" "$HOME/VirtualBox VMs/<машина>/"
   "<комплект>/tools/retarget-vbox-linux.sh" "<...>/<машина>.vbox" "<папка обмена>" "<хранилище>" vboxnet0
   VBoxManage registervm "$HOME/VirtualBox VMs/<машина>/<машина>.vbox"
   VBoxManage snapshot "<машина>" list                # убедиться, что снимки на месте
   ```
   Перенацеливание обязательно, когда `.vbox` пришёл с другой машины: пути общих папок и имя host-only адаптера в нём чужие, **и то же самое записано в каждом снимке** — без правки откат вернёт чужие пути. Проверить, сколько процессоров и памяти прописано в машине: снимок мог быть снят на машине помощнее, и стенд заберёт все ядра хоста.
4. **Разложить остальное:** проекты — в папку обмена, ключи — по путям из `CLAUDE.local.md`, журналы — в `artifacts/`, автопамять — в каталог памяти Claude Code.
5. **Поднять и проверить.** Стенд считается приехавшим, когда прошла доставка с тестами, а не когда скопировались файлы:
   ```bash
   VBoxManage startvm "<машина>" --type headless      # SSH отвечает секунд через 12
   lab/observer.sh                                    # сборка, доставка, /health, тесты обоими путями
   ```
6. **Сказать владельцу числами:** на каких коммитах репозитории, какие снимки есть и какой рабочий, сколько тестов прошло, что лежит в папке обмена и что осталось несделанным по `ПРОЧТИ.md`.

## Шаблон `ПРОЧТИ.md`

Пишется для агента на другой машине, у которого нет ни этого разговора, ни памяти о нём. Коротко и по делу:

```markdown
# Состояние на <дата>

Код и документы: <в гите, коммит X / часть не закоммичена — патч рядом>. Закрытая память: коммит Y.
В комплекте только то, чего в гите нет.

## Что сделано
<по пунктам, с числами прогонов>

## Что осталось
<пронумерованный список: что именно и почему не доделано>

## Как поднять стенд
<рабочая точка отката, ключи, чем перенацеливать пути>

## Как запускать
<команды с переменными, без имён клиентских проектов>

## Грабли, на которые уже наступили
<то, что стоило времени: иначе следующая машина потратит его снова>

## Что в этой папке
<файл — зачем он>
```

## Грабли переезда

- **Ключ, приехавший с Windows, кончается `\r`.** `curl -H "Authorization: Bearer $(cat key)"` подставляет его в заголовок, и сервер отвечает 400 без тела, хотя клиенты на .NET значение обрезают сами. В `lab/observer.sh` это учтено, а в разовых проверках руками ключ читать через `tr -d '[:space:]'`.
- **Кириллица через `cmd` по SSH не проходит.** Всё, где в путях русские буквы, — через `pwsh -NoProfile -EncodedCommand <base64 от UTF-16LE>`.
- **Сеанс SSH нулевой**: окон гостевой системы он не видит. Всё, что трогает окна, — через задачу планировщика (`lab/guest/Invoke-InSession.ps1`).
- **Не использовать `rsync --inplace`** на накопителе: файлы там могут быть жёсткими ссылками на другие копии, и правка на месте испортит и их.
- **Свободное место** проверять заранее: папка машины со снимками — десятки гигабайт, и каждый снимок добавляет к ним.
- **Откат к снимку создаёт новый разностный диск.** Поэтому после дня работы имена файлов в `Snapshots/` меняются, и синхронизация с `--delete` обязательна: иначе на накопителе копятся диски, которых уже нет в конфигурации.
- **`observe run --follow` ждёт конца сеанса** — то есть выхода программы. Проверять живость стенда лучше `lab/observer.sh`, а не длинным сценарием.
